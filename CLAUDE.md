# BadPig – Badminton Pignan (site du club)

Monorepo : `web/` (Angular 22), `bff/` (BFF ASP.NET Core : sert le site, connexion OIDC par cookie, relais `/api` avec YARP) et `api/` (ASP.NET Core, .NET 10, monolithe modulaire en un seul projet). Authentification par Authentik (OIDC), base PostgreSQL 17,
déploiement sur un VPS OVHcloud (Docker, Traefik) par GitHub Actions. Voir `README.md` pour les points d'API et le déploiement.

## Règles de travail (à respecter toujours)

- **Langue** : répondre à l'utilisateur en français. Le **code et les commentaires sont en anglais** (identifiants, noms de tables et de colonnes, messages de log). Seuls restent en français : les textes affichés à l'utilisateur (interface, messages d'erreur montrés à l'écran), les e-mails et les notifications, ainsi que les noms de groupes Authentik (données). Les routes, champs JSON et codes du journal d'audit sont aussi en anglais (les anciennes lignes du journal gardent leurs codes français : `web/src/app/modules/audit/core/audit-actions.ts` les convertit).
- **Style C#** : un `if` / `else` / `foreach` / `while` / `for` dont le corps est **une seule instruction sur une ligne** s'écrit **sans accolades** (`if (x)` puis `return y;` à la ligne suivante, `foreach (var a in b)` puis `a.Run();`) ; dès que le corps tient sur plusieurs lignes, ou qu'un autre bloc de la chaîne `if / else` en a plusieurs, on garde les accolades. La règle est dans `.editorconfig` (`csharp_prefer_braces = when_multiline`).
- **Conditions lisibles** : une condition qui combine plusieurs tests (`&&`, `||`), ou qui appelle une règle dont le résultat se compare à une constante, s'extrait dans une méthode, une propriété ou une fonction locale au **nom explicite** (`CanAddToBoard(target, boardCount)`, `IsLastBoardMember(...)`, `IsWaitingForSignupAsync(...)`, `IsNotAdmin`) plutôt que d'être écrite en ligne dans le `if`. Un nom exprime l'intention métier ; une règle utilisée par une seule feature reste privée dans son handler, une règle partagée va dans le `Core` (`AccountRules.IsClubMember`, `IsOwnAccount`). Préférer le sens positif (`CanX`, `IsX`) et nier à l'appel (`if (!CanX(...))`).
- **Tests obligatoires** : toute nouvelle fonctionnalité de l'API (ou tout changement de comportement) est livrée **avec ses tests d'intégration** dans `api/tests/BadPig.Api.Tests/Features/<Module>/<Cas>Tests.cs` : un `Should_ReturnUnauthorized_When_NobodyIsSignedIn` pour chaque endpoint, puis le cas nominal et chaque erreur documentée (400, 403, 404, 409…). Une fonctionnalité sans tests est incomplète. Les règles de ces tests sont détaillées juste en dessous.
- **Tests de l'API** : projet `api/tests/BadPig.Api.Tests` (xUnit v3 + Testcontainers PostgreSQL + Respawn). On teste **uniquement l'API publique** (requêtes HTTP sur les routes `/api/v1`, statuts et JSON renvoyés), **jamais les détails d'implémentation** (pas d'appel direct aux handlers, validateurs, règles ou `AppDbContext`, pas de lecture de la base : pour vérifier un effet, on relit par l'API). L'application tourne en mémoire (`TestApplication`, `WebApplicationFactory<Program>`) sur un vrai PostgreSQL ; on ne remplace que ce qui est hors de l'application, par des **substituts NSubstitute** (`Substitute.For<...>()`) : Authentik (`IIdentityProvider`, câblé sur un `AccountDirectory` en mémoire qui sert à poser la situation et à relire le résultat), les e-mails (`IEmailSender`), l'horloge (`IDateTimeProvider`, 15 octobre 2026 par défaut) ; la vérification du jeton est remplacée par un `TestAuthHandler`. On vérifie les appels sortants avec `Received()` / `DidNotReceive()` (helpers `AssertEmailSentTo`, `AssertSignupLinkSentTo`…) et on change une réponse avec `Returns(...)`. La personne connectée est donnée par `As(person)` (lue par le `TestAuthHandler`). La base est vidée avant chaque test (Respawn). **Nom d'un test : `Should_ExpectedBehaviorOrAction_When_Condition`** (comportement attendu, puis condition) ; bloc `[Fact]` + corps en Arrange / Act / Assert ; une classe par fonctionnalité (`<Cas>Tests`) dans `Features/<Module>/`, qui hérite de `IntegrationTest` ; les DTO de lecture sont écrits à partir du JSON (`Infrastructure/Dtos.cs`), pas des types de l'API. Toute nouvelle fonctionnalité ou tout changement de comportement s'accompagne de ses tests (succès, 401/403/404/409/400 selon le cas).
- **Une étape à la fois** : quand une action est demandée à l'utilisateur (commande sur le VPS, réglage Authentik, GitHub…),
  donner une seule étape, attendre le résultat, puis continuer.
- **Secrets** : ne jamais écrire dans le code, la documentation, un commit, un message ou un journal : mot de passe, jeton, clé
  privée, chaîne de connexion réelle. Les secrets vivent dans 1Password, les secrets GitHub et les `.env` du serveur (jamais dans Git).
- **Documentation** : tenir à jour `README.md` (points d'API, réglages) à chaque changement ; **il est rédigé en anglais** (comme le code) ; le document d'exploitation du VPS
  est tenu à part par l'utilisateur.
- L'utilisateur travaille sous **Windows** (commandes PowerShell pour son PC) ; le serveur est **Ubuntu** (commandes bash).

## Architecture et règles de sécurité

- Une personne est identifiée par son **UUID Authentik** (`sub` du jeton), jamais par son e-mail ou son nom. Le compte visé par
  une action « sur soi-même » vient du jeton, jamais de la requête.
- Groupes Authentik : `Membres`, `Bureau`, `Admin`. Règles : jamais d'action de gestion sur son propre compte ; les comptes
  `Bureau`/`Admin` ne sont gérables que par un `Admin` ; il reste toujours au moins un membre du bureau et un administrateur.
  Les gardes Angular ne servent qu'à l'affichage : **la vraie protection est dans l'API**.
- **BFF** : le navigateur n'a qu'un cookie `HttpOnly` ; les jetons restent en mémoire du BFF (`Sessions.cs`) qui les renouvelle. Jamais de jeton dans le code Angular ni dans le navigateur. Toute requête `/api` qui modifie doit porter l'en-tête `X-BadPig-CSRF`. La route YARP `/api` est ouverte (`AuthorizationPolicy: anonymous`) : c'est le middleware `/api` de `Program.cs` qui exige la session (401) sauf pour la lecture des annonces et la notification de paiement ; une politique « authenticated » sur la route bloquerait ces deux exceptions avant le middleware. L'API n'est jamais exposée directement (aucun label Traefik).
- **Architecture de l'API** : monolithe modulaire en tranches verticales, **un seul projet** `api/src/BadPig.Api` (pas de dossier `Modules/`) : un dossier par module à la racine (`Administration`, `Profile`) plus `Shared/` (noyau commun : groupes dans `Core/Access/Groups.cs`, `AccountInfo`, `AccountRules`, `IAccountErasure`, `AccountDeletionService`, `IEmailSender`, e-mails, `AppDbContext` commun, et `Identity/` = tout ce qui parle à l'IDP). Chaque module a `Core/` (entités, règles et services communs à tous ses cas d'usage, interfaces que d'autres modules peuvent appeler), `Features/` (un dossier = un namespace par cas d'usage, ce qui change ensemble reste ensemble : `<Cas>Endpoint.cs` (contrôleur HTTP mince, pas de minimal API : route, autorisation, attributs OpenAPI), `<Cas>Handler.cs` (`IHandler<TRequest,TResponse>` qui retourne `Result<TResponse>`, ou `IHandler<TRequest>` qui retourne `Result` quand il ne renvoie rien (204) ; `internal`, toute la logique), `<Cas>Request.cs` et au besoin `<Cas>Response.cs` ; les handlers sont enregistrés automatiquement par `SharedModule.AddHandlers`) et `Infrastructure/` (EF Core, e-mails, tâches de fond). Le fichier `<Module>Module.cs` enregistre les services du module.
  **Regroupement par cohésion (acteur/déclencheur)** : une fonctionnalité va dans le module de ceux qui la déclenchent. `Administration` = opérations administratives du Bureau (invitations, liste, désactiver/réactiver/supprimer un compte, composition du bureau, titres, journal ; tâche de nettoyage automatique) ; `Profile` = ce que la personne fait pour elle-même (mon profil, supprimer mon compte) ; `Announcements` = annonces du club (rédigées par le Bureau, lues par visiteurs et adhérents, likes). `Interclubs` = équipes, capitaines et rencontres des interclubs (le capitaine ou le bureau gère, les adhérents lisent) ; `Shop` = gestion de la boutique par le Bureau (articles, variantes, stock + historique, commandes reçues, remise) ; `Orders` = ce que l'adhérent fait (catalogue, commander, payer, mes commandes, notification de paiement). Les deux modules ne se parlent que par leur `Core` : `Shop.Core` expose `IShopCatalog` (articles proposés, variantes) et `IStockKeeper` (retenir / libérer / vendre du stock) à `Orders` ; `Orders.Core` expose `IOrderBook` (lister les commandes, marquer remise) à `Shop`. Chacun possède ses tables (`Shop` : `shop_products`, `shop_product_variants`, `shop_stock_movements` ; `Orders` : `orders`, `order_lines`) et son `AppDbContext.<Module>.cs`. Leurs features lisent seulement `Core`/`Shared` (dont `IMembershipReader` d'`Administration`). Les adhésions (valider/annuler, entité, lecture du statut) sont dans `Administration` : le module `Memberships` sera recréé si le besoin grandit. Un futur module métier (stock, commandes, événements…) aura ses propres features, y compris celles réservées au Bureau (par la politique `Policies.Board`), sans dépendre d'`Administration`.
  **Règle de cohésion (vertical slice)** : tout type ou méthode utilisé par **une seule** feature est défini **dans le dossier de cette feature** (requête, **réponse**, corps JSON, constantes de code d'audit, textes d'e-mail, énumérations, tâche de fond…). **Un modèle de requête/réponse n'est JAMAIS partagé entre deux features** (une réponse par feature, même si les champs se ressemblent ; pas de `TitleResponse` commun) ; les éléments d'une liste s'appellent `<Feature>Item`. **Une création (POST) renvoie 201 avec le seul identifiant de la ressource** : toutes les créations utilisent le même type `CreatedResponse(Id)` (`Shared/Core/Http`, seule exception à la règle « une réponse par feature », documenté une fois pour toutes) avec `ToCreated()`, jamais l'objet complet ; une modification renvoie 204. Une constante utilisée par une seule feature est définie dans cette feature. Ne vont dans `Core`/`Infrastructure` du module que ce qui sert à **plusieurs** features ou à d'autres modules (entités persistées, règles partagées, interfaces appelées par un autre module, hooks `IAccountErasure`). Le code qui parle à une API externe (IDP, SMTP) est isolé dans `Shared` derrière une interface. Quand un deuxième besoin apparaît, on remonte le type dans `Core`. Une tâche de fond est une feature (dossier `DeleteDisabledAccounts`).
  **Organisation de `Core` (par cohésion, jamais par type technique)** : un type par fichier ; on ne range PAS par genre (`Entities/`, `Services/`, `Models/`, `Interfaces/`…) mais par sujet métier qui change ensemble (les namespaces restent `BadPig.<Module>.Core`). `Administration/Core` : `Memberships/` (entité, types, états, lecteur), `Seasons/` (entité, règles, conflits, validation), `Board/` (composition, règles, codes d'audit communs), `Titles/`, `Accounts/` (compte désactivé, accès, notification de suppression), `Invitations/`, `Audit/`. `Shared/Core` : `Handling/` (Result, Error, ErrorType, IHandler, ResultExtensions), `Paging/`, `Access/` (groupes, politiques, personne connectée), `Accounts/` (AccountInfo, règles, suppression, effacement RGPD), `Http/`, `Mail/`, `Time/`. Le module `Profile` n'a pas de `Core` (rien n'y est partagé).
  **Dépendances d'une feature** : une feature ne dépend **jamais** du dossier `Infrastructure` de son module (ni d'un autre) : elle utilise `Core` (entités, règles, services partagés), `Shared` (dont `AppDbContext` dans `Shared/Persistence`, `IIdentityProvider`, `IEmailSender`, `IUserContext`) et ses propres types. `Infrastructure` ne contient que les implémentations d'interfaces du `Core` (lecture pour un autre module, audit, effacement RGPD) et la configuration EF. Pas de « store » ou de service fourre-tout : la logique d'une seule feature est dans son handler. Une action = une feature (ex. `AddToBoard` et `RemoveFromBoard`, pas un `ChangeBoard` à deux sens).
  **Result pattern** (`Shared/Core/Handling`) : un handler ne lève pas d'exception pour un cas métier, il **retourne** un résultat. `Result<TValue>` porte une valeur ou des `Error` ; `Result` (sans valeur) se termine par `Result.Success()`. Les conversions sont implicites : on écrit `return valeur;`, `return Error.Conflict("…");`, `return validation.Errors;` ou `return autreResultat.Errors;`. Une `Error` a un `Type` (`ErrorType` : `Validation` 400, `Unauthorized` 401, `Forbidden` 403, `NotFound` 404, `Conflict` 409, `BadGateway` 502, `Unexpected`/`Failure` 500), un `Title` (message court **en français** montré à la personne) et un `Detail` optionnel ; pour `Error.Validation(champ, message)` le titre est le nom du champ. L'endpoint transforme le résultat par `ToOk()` (200), `ToCreated()` (201), `ToNoContent()` (204) : les erreurs de validation donnent un seul 400 qui les liste toutes, sinon la première erreur décide du statut (404 sans corps). Une configuration serveur manquante est une `Error.Unexpected(...)` (500).
  **Horloge** : jamais de `DateTime.UtcNow` / `DateTimeOffset.UtcNow` dans le code ; on injecte `IDateTimeProvider` (`Shared/Core`, implémenté par `SystemDateTimeProvider`) pour que les tests unitaires maîtrisent le temps. Les règles pures (ex. `Seasons`) reçoivent la date en paramètre. **Heure du club** : le club vit à Paris ; la conversion est dans `ClubTime` (`Shared/Core/Time` : `Today`, `TimeOfDay`, `Now`), seul endroit qui connaît le fuseau (`SeasonRules.Today` s'appuie dessus). Jamais de `TimeZoneInfo` ailleurs.
  **Listes** : tout endpoint qui renvoie une liste est **paginé, triable et filtrable** : la requête de la feature hérite de `ListQuery` (`search`, `sort`, `direction`, `page`, `pageSize` ; 25 par page par défaut, 100 au plus), le handler renvoie un `PagedResponse<T>` (`items`, `page`, `pageSize`, `totalCount`, `totalPages`) ; les noms de personnes et de saisons se trient par `AlphabeticalComparer.Instance` (sans accents ni majuscules ; l'API tourne en `InvariantGlobalization`, où les comparateurs de culture trient par code, donc « Émilie » après « Zoé »), jamais par `StringComparer.*` ; chaque feature décide des champs triables (tri inconnu → 400) et de ce que la recherche regarde. Côté site : `Page<T>`, `ListState` (shared/core/page.ts, qui porte aussi la taille de page choisie) et les composants `app-search-box`, `app-sort-select`, `app-sort-header`, `app-page-size` (10/25/50/100) et `app-pager` (shared/ui/list-controls.ts).
  **Audit par module** : il n'y a pas de module Audit commun. Un module qui a besoin d'un audit définit le sien (entité, table, interface dans son `Core`). Aujourd'hui `Administration` (`IAdministrationAudit`) et `Shop` (`IShopAudit`, table `shop_audit_log`, features `ListShopAuditLog` ; chaque handler de gestion de la boutique l'appelle après succès ; sujet = nom copié de l'article/variante, pas de donnée d'adhérent) en ont un : `IAdministrationAudit` (table `administration_audit_log`), qui trace aussi la validation et l'annulation des adhésions ; le « Journal » du site l'affiche. `Profile` n'écrit dans le journal d'Administration que la suppression de son propre compte (interface du `Core`).
  **Prestataire de paiement** : tout ce qui parle à Stripe est dans `Shared/Payments/` (`StripePaymentProvider`, `StripeOptions` : `internal`) ; les modules n'utilisent que `IPaymentProvider` (ouvrir une page de paiement, lire son état, la fermer, vérifier/lire une notification signée). Changer de prestataire = remplacer ce dossier. `Program.cs` n'appelle que `AddPaymentProvider`. Les montants sont des **centimes entiers** (`int`) partout. **Fournisseur d'identité (IDP)** : tout ce qui parle à Authentik est dans `Shared/Identity/` (`AuthentikClient`, options, modèles, `AuthentikIdentityProvider` : tous `internal`). Les modules n'utilisent que `IIdentityProvider` (chercher, lister, créer, modifier, activer/désactiver, supprimer, groupes, lien d'inscription) et `AccountInfo`. Changer d'IDP = remplacer ce dossier, sans toucher aux features. `Program.cs` n'appelle que `AddIdentityProvider` et `AddIdentityAuthentication` (la section de configuration reste `Authentik`). **Validation des entrées (FluentValidation)** : chaque requête qui a des règles a un `<Feature>Validator : AbstractValidator<<Feature>Request>` dans le dossier de sa feature (`internal sealed`, messages d'erreur en français, enregistrés automatiquement par `AddValidatorsFromAssembly`). **Le handler valide lui-même sa requête, en toute première instruction** (pas de décorateur ni de pipeline caché, pour que le déroulement soit lisible) : il reçoit `IValidator<<Feature>Request>` par son constructeur, appelle `await validator.ValidateAsync(request, ct)` et, si `!validation.IsValid`, renvoie `validation.Errors` (conversion implicite en erreurs de validation ; réponse 400 avec les champs en erreur, noms en camelCase) ; le reste du handler peut alors supposer la requête valide. Les identifiants de route se valident par `MustBeGuid()` ; les listes héritent de `ListQueryValidator<T>` et déclarent leurs champs triables par `MustBeSortableOn(...)`. Les règles communes à plusieurs features sont des extensions FluentValidation dans `Core` (ex. `MustBeAFee`, `MustBeATitleLabel`, `MustBeAnEmail`) ; on n'utilise que des extensions génériques (`Must`, `NotEmpty`, `NotNull`) pour éviter les avertissements de nullabilité. Les règles qui demandent la base (unicité, chevauchement, existence) restent dans le handler (réponse 404/409). **JSON** : camelCase par défaut (configuré dans `Program.cs`), donc pas de `[JsonPropertyName]` sur les requêtes/réponses.
  **Documentation OpenAPI** : bibliothèque native `Microsoft.AspNetCore.OpenApi`. Chaque endpoint porte `[Tags("<Module>")]`, `[EndpointSummary]`, `[EndpointDescription]` et un `[ProducesResponseType]` par réponse possible ; les commentaires `///` des requêtes/réponses alimentent les schémas. Le document est servi sur `/api/v1/openapi/v1.json` (réservé au Bureau, via la session du site). Swagger UI (`Swashbuckle.AspNetCore.SwaggerUI`) est activé uniquement en Development, sur `/api/v1/swagger`, à ouvrir via le site local (BFF). Chaque action de contrôleur porte aussi des commentaires XML `/// <param name="id">` (paramètres de route) et `/// <response code="NNN">` (une phrase par code de réponse, y compris les erreurs), et chaque champ des réponses/requêtes est décrit par un `/// <param>` sur le record (valeurs possibles des champs à codes : statuts, états, groupes). Les règles communes (401/403, format des erreurs, pagination) sont décrites dans la description du document (`Program.cs`) ; chaque controller d'API porte `[ProducesResponseType(401)]`. **Sur une action de contrôleur, documenter tous les paramètres (`id`, `body`, `ct`) ou aucun** : une documentation partielle déclenche l'avertissement CS1573. Un nouvel endpoint sans ces attributs et commentaires est incomplet.
  **Règle d'isolation (non vérifiée par le compilateur)** : un module n'utilise d'un autre module que son dossier `Core` (interfaces, types de contrat) et `Shared`, jamais ses `Features` ni son `Infrastructure`, ni ses `DbSet`. Pour qu'un module ait besoin des données d'un autre, ajouter une interface dans le `Core` du module propriétaire. Une nouvelle fonctionnalité = un nouveau dossier dans `Features/` du bon module. Principes SOLID : dépendre d'interfaces entre modules, interfaces petites, ajout de comportement par de nouvelles classes (ex. un module de plus qui implémente `IAccountErasure`) plutôt que par modification des existantes.
- **Architecture du site Angular** (même principe que l'API) : `web/src/app/shared/` = noyau commun (`core/` : types et règles, par ex. `AdminUser`, `Groups` ; `infrastructure/` : `AuthService`, gardes, intercepteur `/api`, `UsersDirectory`, `AdminActivity`) ; `web/src/app/modules/{accounts,memberships,board,audit,announcements,interclubs,orders,shop}`, chacun avec `core/`, `features/` (un dossier par cas d'usage ou composant de page), `infrastructure/` (service `*.api.ts` qui appelle l'API), `<module>.routes.ts` et un `index.ts` (seule porte d'entrée publique du module) ; l'hôte (`app.ts`, `app.routes.ts`, `admin/`) assemble les modules. **Un module n'importe jamais un autre module** (seulement `shared`) ; l'hôte n'importe un module que par son `index.ts`. Partage : composant commun `app-share-panel` (`shared/ui/share-panel.ts` : WhatsApp `wa.me`, partage natif, copie du lien, QR code dessiné en SVG par `qrcode-generator` et téléchargeable en PNG, rien n'est envoyé à un service externe) à poser sur toute page partageable (annonce, futurs événements). Aperçu de lien : le BFF (`LinkPreview.cs`) renvoie aux robots de messagerie (WhatsApp, Telegram, Facebook…) la page du site avec les balises Open Graph d'une annonce **publique** (API appelée sans jeton) ; jamais d'information d'une annonce interne ou d'un brouillon. Les actions du bureau sur une ligne d'utilisateur sont des composants de leur module (`app-account-actions`, `app-membership-actions`, `app-board-actions`, `app-title-select`) posés par la page `admin/admin-users.page.ts`, qui fournit `AdminActivity`. Le contrôle `node scripts/check-module-boundaries.mjs` (lancé aussi par le Dockerfile) vérifie ces règles. Les textes visibles restent en français, le code en anglais. Modules boutique (miroir de l'API) : `orders` (adhérents : `/shop` catalogue + panier puis redirection vers la page de paiement Stripe `checkoutUrl`, `/shop/orders` mes commandes, `/shop/orders/:id` détail : payer, annuler, actualisation automatique au retour de Stripe ; `memberGuard`) et `shop` (bureau : `/admin/shop` articles/variantes/stock avec `app-product-card` et `app-variant-row` (réapprovisionner, corriger, modifier, supprimer ; prix saisis en euros, envoyés en centimes), `/admin/shop/orders` commandes reçues avec « Marquer remise », `/admin/shop/variants/:id/history` historique du stock ; `boardGuard`). Module `announcements` : pages publiques `/announcements` (liste) et `/announcements/:id` (détail : texte, affiche, vidéos, liens Instagram/Facebook, pièces jointes, like), pages du bureau `/admin/announcements` (liste, filtres, actions rapides), `/admin/announcements/new` et `/:id/edit` (formulaire avec éditeur de texte riche maison `app-rich-text-editor`, sans bibliothèque ; l'API nettoie encore le HTML). Sondage = annonce à part entière (page `/admin/announcements/new-poll`, même formulaire `announcement-form` en mode sondage) : composant `app-announcement-poll` (formulaire de réponse pour adhérents/bureau tant que le sondage est ouvert, résultats en barres une fois clos, noms pour le bureau si non anonyme) affiché dans le détail, et `app-poll-editor` (champs : choix, réponse unique/multiple, anonyme, date limite). Commentaires : composant `app-announcement-comments` sous le détail (adhérents/bureau, fil de discussion style WhatsApp : bulles, citation cliquable, bandeau « Réponse à … » au-dessus du champ, masqué si `commentsEnabled` est faux) ; case « Autoriser les adhérents à commenter » dans `announcement-form`. Une vidéo = un lien YouTube/Vimeo seul sur sa ligne dans le texte (`splitBody` dans `core/media-links.ts`), lecteur chargé au clic seulement (aucune donnée envoyée avant) ; les liens Instagram/Facebook sont de simples liens.
- **Navigation du site** : l'en-tête ne liste que les sections (Accueil, Annonces, Interclubs, Boutique, Administration) ; le profil et la déconnexion sont dans le menu du compte. Une section à plusieurs pages pose `app-tabs` sous son titre (liste de `Tab` dans le `core/` du module). Une page reprise porte `host: { class: 'bleed' }` et se met en page elle-même (`<main class="container stack stack-l">`).
- **Kit de page (tous les écrans se ressemblent)** : un écran = `host: { class: 'bleed' }` + `<main class="container stack stack-l" style="padding-block: var(--space-30) var(--space-60)">`, puis **toujours** `<app-page-head [trail]="trail" title="…" lead="…" />` (`shared/ui/page-head.ts`) : le **fil d'Ariane remplace tout lien « ← Retour »**, le titre de page est un `h1` à `--text-h2`. Ensuite, dans cet ordre : la sous-navigation de section (`app-tabs`), les messages (`.alert alert-success|error|warning|info`, jamais un simple texte coloré), l'action principale, les filtres, la liste. **Boutons** : une seule action principale `.btn` par écran ; les autres `.btn-ghost` ; une action destructrice `.btn-danger` (avec confirmation) ; une bascule `.btn-outline` + `aria-pressed` (« J'aime ») ; les actions rares d'une ligne dans un `details.more` « Plus d'actions ». **Filtres** : des pastilles `.chip` avec `aria-pressed`, jamais une case à cocher ni une liste déroulante ; recherche `app-search-box`, tri `app-sort-select` ; quand une liste déroulante reste nécessaire, la ligne de filtres est un `div.filters` (classe globale : la recherche prend la place restante, les `select.select` gardent la leur). **Titres** : le titre de page est le `h1` d'`app-page-head` ; les titres de section d'une page sont des `h2` (le système les met un cran en dessous), le titre d'une carte un `h2`/`h3` `.card-title`. **Supprimer** : toute action destructrice porte `.btn-danger` (framboise), jamais la même apparence qu'une action ordinaire. **Texte secondaire** : `.small-text` (la classe `.hint` n'existe plus). **Panneau dépliant** : un formulaire que l'on ouvre au besoin s'écrit `<details class="card panel">` + `<summary class="card-title">` (le résumé est le titre, avec un chevron ; le composant posé à l'intérieur ne répète pas ce titre). **Listes** : `.rtable` + `data-label` par cellule (cartes sous 768) et `app-pager`. **États** : `.skeleton` pendant le chargement, `.empty` quand il n'y a rien.
- **Design du site** : le système de design est dans `web/src/styles.css` (brief : `docs/design-brief.md`). **Jamais de couleur en dur dans un composant** : seulement `var(--jeton-de-rôle)` (niveau 2 : `--color-text`, `--button-primary-background`, `--badge-*`, `--alert-*`, `--focus-ring`…), jamais un jeton de palette (niveau 1 : `--primary-base`…) sauf dans `:root`. Même règle pour les tailles, espacements, rayons, ombres et durées (`--text-*`, `--space-*`, `--radius-*`, `--shadow-*`, `--duration-*`). Base `1rem = 10px` : écrire les valeurs en rem sur cette base. Mobile d'abord ; les paliers 768 / 1024 s'écrivent `@container vp (min-width: 76.8rem)` (c'est `app-root` qui porte le conteneur). Un menu d'actions s'écrit `<details class="more">` (ou `details.account` pour le compte) et le composant importe la directive `MenuDetails` (`shared/ui/menu-details.ts`), qui ferme le menu au clic en dehors et à la touche Échap. Réutiliser les classes globales (`.btn`, `.card`, `.highlight-*`, `.alert-*`, `.input`, `.rtable`, `.empty`, `.skeleton`, `.stack`, `.cols`…) plutôt que de redéfinir un style local ; un style de composant ne sert qu'à ce qui lui est propre. Zones tactiles d'au moins `--tap-min`, focus visible, et jamais d'information portée par la seule couleur. Le bloc `TRANSITION` en fin de `styles.css` n'existe que le temps de reprendre tous les écrans : ne rien y ajouter.
- **Personne connectée** : le code de l'API lit la personne authentifiée **uniquement** par l'interface `IUserContext` (`Shared/Core`, implémentée par `HttpUserContext` : `AccountId`, `DisplayName`, `IsInGroup(ClubGroup)`), injectée dans les contrôleurs et services ; ne pas utiliser `User` / `ClaimsPrincipal` dans les cas d'usage. `IAuditLog.RecordAsync(action, targetId, ct)` prend l'auteur dans `IUserContext`. Seules les politiques d'autorisation de `Program.cs` lisent le jeton directement. Les groupes sont l'enum `ClubGroup` (`Members`, `Board`, `Admin`, dans `Shared/Core/Access/Groups.cs`, qui donne aussi leur nom Authentik par `Groups.NameOf`) : utiliser `IsInGroup(ClubGroup.X)` (utilisateur courant ou `AccountInfo`) et `IAccountDirectory.AddToGroupAsync(id, ClubGroup.X, ct)`, jamais de chaîne de groupe dans les cas d'usage.
- Authentik est appelé par `AuthentikClient` (compte de service), uniquement depuis `Shared/Identity/`. **Toujours envoyer un `Content-Length`** (`StringContent`) :
  Authentik ignore les corps « chunked ».
- Base de données : EF Core (PostgreSQL), **un seul `AppDbContext`** en classes partielles : chaque module a son fichier `Infrastructure/AppDbContext.<Module>.cs` avec ses `DbSet` et la configuration de ses entités (mêmes noms de tables et colonnes que les scripts SQL). Le schéma est encore créé par les scripts
  `api/src/BadPig.Api/Migrations/NNN_*.sql`, appliqués au démarrage : **ne jamais modifier un script déjà appliqué**, ajouter un nouveau fichier
  (et adapter la partie du module dans `AppDbContext`). Des migrations EF par module remplaceront ces scripts.
- RGPD : le **journal d'audit** (`administration_audit_log`, immuable) ne contient que des UUID pour les personnes visées (pas de nom ni d'e-mail) et
  le nom de la personne du bureau qui agit. Supprimer un compte efface ses lignes dans `invitations`, `memberships`,
  `board_titles`, `disabled_accounts`. Toute nouvelle table contenant des données personnelles doit être vidée à la suppression
  d'un compte : le module propriétaire implémente `IAccountErasure` (comptes supprimés par le titulaire, par le bureau, ou automatiquement par `DisabledAccountCleanup`).
- Chaque action du bureau sur une personne est tracée dans le journal (`IAdministrationAudit.RecordAsync`) ; les libellés sont dans
  `web/src/app/modules/audit/core/audit-actions.ts`.
- E-mails aux personnes concernées : `IEmailSender` (Shared) ; les textes français sont dans les classes `*Notifications` de chaque module (Postfix du VPS, réseau Docker `mail`). Un échec d'envoi n'annule jamais
  l'action. Ne pas décrire dans les e-mails des fonctionnalités qui peuvent évoluer.

## Règles métier

- **Saisons (entité `Season`)** : gérées par le bureau (features `CreateSeason`, `UpdateSeason`, `DeleteSeason`, `ListSeasons`, `ListSeasonStatistics`) : nom unique, dates sans chevauchement (par défaut 1er septembre → 31 août), tolérance en jours (30 par défaut) et deux cotisations (`InternalFee` pour un licencié du club, `ExternalFee` pour un licencié dans un autre club). Les règles pures sont dans `SeasonRules` (saison en cours = celle qui contient la date du jour à Paris, sinon la dernière commencée ; état d'une adhésion `valid`/`grace`/`to_validate`).
- **Séances et vacances scolaires** : le club joue **les mardis, mercredis et vendredis de 20 h à 23 h** ; l'horaire hebdomadaire est écrit une seule fois, dans `ClubSessions` (`Administration/Core/Sessions`). Le bureau saisit les **vacances scolaires** de chaque saison (`SchoolHoliday`, table `school_holidays`, supprimées avec la saison ; features `CreateSchoolHoliday`, `UpdateSchoolHoliday`, `DeleteSchoolHoliday`, `ListSchoolHolidays` sous `/admin/seasons/{id}/holidays`, tracées dans le journal) : dates comprises dans la saison, sans chevauchement, les deux jours inclus. `SessionRules` (règles pures) en déduit s'il y a séance un jour donné et les prochaines séances ; `ListClubSessions` (`GET /club/sessions`, **anonyme**, le BFF laisse passer cette lecture comme celle des annonces) les sert au site, qui affiche la même information aux visiteurs et aux adhérents (`app-club-sessions`, `shared/ui`). Tout est calculé à l'heure de Paris (`ClubTime`), jamais dans le navigateur.
- **Adhésion** : une ligne par personne et par saison (`memberships`), avec le type (`internal`/`external`, constantes `MembershipKinds`) et le **montant copié de la saison à la validation** (changer une cotisation ensuite ne modifie pas l'historique). Le type est choisi à l'invitation (`Invitation.MembershipKind`) et peut être changé à la validation. Dès la fin de la tolérance, un adhérent non validé garde son compte mais perd l'espace membres. Bureau et admins ne sont pas concernés. Un membre du bureau ne valide pas sa propre adhésion. Le journal d'audit garde le **nom** de la saison (`membership.validated.2026-2027` ; les anciennes lignes portent l'année).
- **Licence et date d'adhésion** : le **numéro de licence** à la fédération (FFBaD) est une donnée du club, pas de l'IDP : table `member_licences` (une ligne par compte, migration 031), possédée par `Administration` (`Core/Licences` : entité, `LicenceRules` — lettres, chiffres et tirets, 20 caractères au plus, vide = retrait — et `ILicenceBook`, le seul accès pour le module `Profile`). Il se modifie **par la personne elle-même** (`SetMyLicence`, `PUT /me/licence`, compte pris dans le jeton) **ou par le bureau** (`SetMemberLicence`, `PUT /admin/users/{id}/licence`, tracé dans le journal : `licence.updated`) ; il apparaît dans la liste des adhérents (`ListUsers`, colonne et recherche). **Un numéro renseigné est unique dans le club** : `ILicenceBook.IsTakenAsync` (comparaison sans tenir compte de la casse) et les deux handlers répondent 409 ; l'index unique `ux_member_licences_number` sur `upper(number)` (migration 032) le garantit en base. Un numéro vide ne bloque personne. RGPD : `AdministrationEraser` l'efface avec le compte. La **date d'adhésion** n'est pas stockée : `MembershipStatus.MemberSince` est la date de la **première adhésion validée** de la personne, servie par `GET /me` et affichée dans son profil.
- **Annonces (module `Announcements`)** : `kind` `internal` (adhérents) ou `public` (visiteurs) ; brouillon par défaut ; tout membre du bureau peut modifier, publier, épingler et supprimer n'importe quelle annonce ; pas de journal d'audit. Audience (`AnnouncementAudience`) : `Visitor` = anonyme ou membre dont l'adhésion est `to_validate` (via `IMembershipReader`), `Member` = adhérent, `Board` ; `VisibleTo(audience)` est l'unique filtre de visibilité (Board : tout ; Member : publiées internes + publiques ; Visitor : publiées publiques). L'auteur n'est exposé qu'au Bureau ; likes réservés aux adhérents/bureau (null pour un visiteur). Ordre : épinglées d'abord, puis date de publication décroissante. Le HTML est nettoyé par `IRichText` (HtmlSanitizer, liste blanche) ; vidéos et liens sociaux = de simples liens dans le texte (pas de champ dédié) : le site transforme un paragraphe qui ne contient qu'un lien YouTube/Vimeo en lecteur chargé au clic (RGPD), les autres liens restent des liens ; fichiers sur disque (`IAnnouncementFileStore`, volume `Announcements__StoragePath`, à sauvegarder), type décidé par l'extension, affiche 5 Mo, pièce jointe 10 Mo, 10 pièces au plus. Les lectures `GET /api/v1/announcements*` sont anonymes (le BFF les laisse passer sans session). Chaque annonce a une forme `form` (`text` ou `poll`). Date de fin `ExpiresOn` (date de Paris, 90 jours après la création par défaut, jamais dans le passé à la saisie ; `null` à la modification = inchangée) : périmée = cachée aux visiteurs et adhérents (le `VisibleTo(audience, today)` reçoit la date du jour, `AnnouncementViewer.Today`), visible du bureau avec `isExpired`, puis supprimée (fichiers et likes) par la tâche de fond `ExpiredAnnouncementCleanup` (toutes les 6 h). `AnnouncementsEraser` (`IAccountErasure`) supprime les likes et anonymise l'auteur (« Ancien membre du bureau »).
- **Sondages** (module `Announcements`, `Core/Polls`) : un sondage est une **annonce à part entière** (`Announcement.Form` = `AnnouncementForms.Poll`, `text` pour les autres), créé par `CreatePollAnnouncement` (`POST /admin/announcements/polls` : titre = question, texte facultatif, 2 à 10 choix, réponse unique ou multiple, anonyme ou non, date limite `ClosesOn` obligatoire, jamais dans le passé) ; il n'existe aucune façon d'attacher un sondage à une annonce texte. `AnnouncementPoll`/`PollOption`/`PollVote` en dépendent (cascade). Ouvert jusqu'à la date limite **incluse** (`PollRules.IsClosed`). Réponses : adhérents et bureau seulement (`AnnouncementViewer`, 403 pour un visiteur), sondage publié et lisible, la nouvelle réponse remplace l'ancienne, 409 une fois clos. Les choix ne changent jamais ; la date limite se change à part (`ChangePollDeadline`) tant que le sondage est ouvert. Le sondage reste affiché au moins jusqu'à la clôture (`ExpiresOn` relevé, ou 400 à la création / modification). Le texte est obligatoire pour une annonce texte, facultatif pour un sondage (`UpdateAnnouncement` selon `Form`). Résultats (`VoteCount`, `ResultsVisible`) : pour les adhérents seulement une fois clos ; **le bureau les voit à tout moment** (provisoires avant la clôture) ; `Voters` (noms) seulement pour le bureau et si le sondage n'est pas anonyme (clos ou non) ; avant la clôture un adhérent ne voit que `ParticipantCount`. L'anonymat est applicatif (la base garde `member_id`). `AnnouncementsEraser` efface les réponses d'un compte supprimé.
- **Commentaires** (module `Announcements`, `Core/Comments`) : `AnnouncementComment` (texte brut 1 à 1000, nom de l'auteur copié, `ParentId` nullable = message cité, style WhatsApp : n'importe quel message de l'annonce, sans clé étrangère, le message cité peut avoir disparu), features `AddAnnouncementComment` (corps `text`, `parentId?`), `ListAnnouncementComments` (conversation à plat paginée, tri `createdAt`, recherche ; `ReplyTo` = citation `{Id, AuthorName, Excerpt, IsDeleted}` calculée à la lecture, « supprimé » si le message cité n'existe plus), `DeleteAnnouncementComment`. Visibles et écrits par tous les adhérents et le bureau (`AnnouncementViewer`, 403 pour un visiteur) sur une annonce ou un sondage publié et lisible (sinon 404). `Announcement.CommentsEnabled` (défaut `true`, choisi à la création et à la modification par le bureau, `null` = inchangé) : fermé, `AddAnnouncementComment` répond 409, le site masque la section, la liste et la suppression restent possibles. Suppression : `CommentRules.CanDelete` = l'auteur ou n'importe quel membre du bureau (403 sinon). Supprimer un message ne supprime pas ceux qui le citent. Pas de modification. Supprimés en cascade avec l'annonce et par `AnnouncementsEraser` avec le compte de leur auteur. **E-mails** : `AddAnnouncementCommentHandler` prévient l'auteur de l'annonce (`Nouveau commentaire…`) et l'auteur du message cité (`… a répondu à votre commentaire`) via `IIdentityProvider.FindAsync` + `IEmailSender` ; textes dans `CommentNotifications` (feature), jamais à soi-même, un seul e-mail si les deux destinataires sont la même personne (e-mail de réponse), compte absent/désactivé ignoré, échec d'envoi journalisé sans annuler le commentaire. Lien optionnel via `AnnouncementLinks` (réglage `Announcements:SiteUrl`).
- **Boutique (modules `Shop` et `Orders`)** : `Product` (nom, description, `IsActive`) → `ProductVariant` (libellé unique dans l'article, `PriceCents`, `Quantity` = en rayon réservé compris, `ReservedQuantity` = retenu par des commandes non payées, `LowStockThreshold`, `IsActive` ; `Available = Quantity - ReservedQuantity`) et `StockMovement` (historique : `restock`, `correction`, `sale`, auteur copié) sont à `Shop` ; `Order` (statuts `OrderStatuses` : `pending` → `paid` → `delivered`, ou `cancelled` / `expired`) + `OrderLine` (nom, libellé, prix **copiés** ; `VariantId` sans clé étrangère) sont à `Orders`. Features de `Shop` (Bureau) : `CreateProduct`, `UpdateProduct`, `DeleteProduct`, `ListProducts`, `CreateVariant`, `UpdateVariant`, `DeleteVariant`, `RestockVariant`, `CorrectVariantStock`, `ListStockMovements`, `ListShopOrders`, `MarkOrderDelivered` (ces deux-là passent par `IOrderBook`) ; de `Orders` (adhérents) : `ListCatalog` (par `IShopCatalog`), `CreateOrder`, `ListMyOrders`, `GetMyOrder`, `CancelMyOrder`, `ReceivePaymentNotification` (Stripe, anonyme, signature obligatoire) et la tâche de fond `ReleaseExpiredOrders` (`UnpaidOrderCleanup`). Accès : `OrderAccess.CanOrderAsync` (bureau/admin, ou membre dont l'adhésion n'est pas `to_validate`, comme `AnnouncementViewer`). Le réglage du site s'appelle `Shop__SiteUrl` (`OrderLinks`).
  **Stock sans survente** : le stock n'est jamais modifié par lecture-puis-écriture mais par `ExecuteUpdateAsync` conditionnel/relatif dans `StockKeeper` (retenir : `... WHERE quantity - reserved >= n` ; vendre/libérer : `reserved - n`) ; la base garde `reserved_quantity <= quantity`. `CreateOrder` retient le stock dans une transaction (tout ou rien), crée la commande et la page de paiement (échec → rien n'est gardé), durée `OrderRules.Reservation` = 35 minutes (Stripe exige au moins 30). `OrderSettlement` (`Orders/Core`) règle une commande une seule fois (`MarkPaidAsync`, `ReleaseAsync` commencent par une mise à jour conditionnelle du statut `pending`) pour la notification ET pour la lecture de la commande (`GetMyOrder` interroge le prestataire) ; `ReleaseExpiredAsync` interroge le prestataire avant de libérer (un paiement tardif n'est pas perdu) et est aussi appelé par les listes. Une commande payée annulée/expirée entre-temps est seulement journalisée (remboursement manuel). Un échec d'e-mail ne casse jamais le règlement ; à chaque commande payée (une seule fois, grâce au règlement conditionnel) `OrderSettlement` envoie l'e-mail de confirmation à l'acheteur puis un e-mail « Nouvelle commande de … » au bureau (réglage `Shop__NotificationEmail`, sinon chaque membre actif Bureau/Admin via `IIdentityProvider.ListAsync`), chacun dans son propre `try`. **Stock bas** : `IStockKeeper.AlertLowStockAsync` (appelé par `OrderSettlement` après l'enregistrement de la vente) envoie `LowStockNotifications` au bureau via `BoardMailer` (`Shared/Core/Mail` : adresse du club `Shop__NotificationEmail` de `ShopOptions`, sinon chaque membre actif Bureau/Admin) quand le disponible d'une variante avec seuil > 0 est ≤ seuil ; `ProductVariant.LowStockAlerted` (migration 019) garantit un seul e-mail par passage sous le seuil (mise à jour conditionnelle) et est remis à faux par `LowStockAlerts.ClearIfRecoveredAsync` dès que le stock repasse au-dessus (réapprovisionnement, correction, modification de variante, libération de stock). Un échec d'envoi est journalisé seulement. **Image d'article** : `ProductImage` (table `shop_product_images`, migration 022, octets à part pour que les listes ne les lisent jamais, cascade avec l'article) ; features `SetProductImage` / `RemoveProductImage` (Shop, bureau, tracées dans `IShopAudit`), lecture par `GetProductImage` (Orders, via `IShopCatalog.GetImageAsync(id, includeHidden)` ; le bureau voit aussi les articles masqués) ; les listes donnent `ImageVersion` (millisecondes Unix de la dernière modification, `null` sans image) pour l'adresse `…/image?v=` ; le type vient des premiers octets du fichier. Une seule commande non payée par personne. RGPD : `OrdersEraser` anonymise les commandes (comptables) et annule les non payées ; `ShopEraser` efface l'auteur de l'historique du stock ; `OrdersEraser` remplace aussi le nom de qui a remis une commande (`delivered_by_*`, migration 020) par « Ancien membre du bureau ».
- **Interclubs (module `Interclubs`)** : `Team` (nom ex. `D4`, `Season` = libellé libre « 2026-2027 », `CaptainId` nullable, unique par saison + nom sans tenir compte de la casse) et `Fixture` (rencontre : `PlayedOn` date, `StartTime` facultatif, `Opponent` = club adverse, `Venue` = `home`/`away` (`FixtureVenues`), `Place` facultatif ; supprimée avec son équipe). Le **bureau** crée les équipes et désigne le capitaine (un membre actif du club, pas forcément du bureau, aucun groupe Authentik de plus) ; le **capitaine d'une équipe ou le bureau** gère ses rencontres (`InterclubAccess.CanManageFixtures`, 403 sinon) ; tous les adhérents à jour et le bureau lisent (`InterclubAccess.CanViewAsync`, même règle que la boutique). Les noms des capitaines viennent d'`IIdentityProvider` (jamais copiés). `InterclubsEraser` retire une personne supprimée du poste de capitaine. **Propositions de dates** (fonctionnalité **masquée côté site** depuis le 31/10/2026, à la demande du club : API et pages conservées, onglet et routes en commentaire) : le capitaine (ou le bureau) offre 2 à 10 dates (`DateProposal` + `ProposedDate`, adversaire et lieu communs) pour la prochaine rencontre ; **seuls les joueurs de l'équipe** (`TeamMember`, effectif choisi par le capitaine ou le bureau parmi tous les adhérents actifs, `AddTeamMember`/`RemoveTeamMember`/`ListTeamCandidates`) répondent `yes`/`maybe`/`no` par date (`DateAnswer`, une ligne par personne et date, **effacée avec le compte** par `InterclubsEraser`) tant qu'aucune date n'est choisie ; seuls le capitaine et le bureau voient les noms ; `ChooseProposedDate` crée la `Fixture` et renseigne `DateProposal.FixtureId` (proposition fermée). Retirer un joueur supprime ses réponses aux propositions encore ouvertes ; `InterclubsEraser` le retire aussi de ses équipes. Le capitaine n'est joueur que s'il se met dans l'effectif. **Composition et score** : une rencontre a 7 matchs (`MatchSlots` : `SD` simple dame, `MX1`/`MX2` mixtes, `DD` double dame, `DH` double homme, `SH1`/`SH2` simples hommes), une ligne `FixtureMatch` par rencontre et match (`Player1Id`, `Player2Id` pour un double, et jusqu'à 3 sets `Set1Club`/`Set1Opponent`… ). **Règles du jeu** dans `MatchRules` : un set se gagne à **15 points avec 2 points d'écart** ; à partir de 14-14, 2 points d'écart ou le premier à **21** (sets valides : 15-0…15-13, 16-14…20-18, 21-19, 21-20 ; le plus haut score gagne le set), un match a **2 ou 3 sets** et est gagné avec **2 sets** (il s'arrête dès que l'un en a 2) ; **forfait et abandon** (`FixtureMatch.Ending` = `played`/`forfeit`/`retirement` (`MatchEndings`), `Withdrawn` = `club`/`opponent` (`MatchSides`), migration 028) : le camp qui déclare forfait (aucun set) ou abandonne (sets terminés conservés, match non décidé) **perd le match** ; **personne ne saisit le gagnant** : `FixtureMatch.Outcome` (`won`/`lost`) est calculé depuis les sets ou le camp concerné, et le score de la rencontre (`MatchScore`) est le nombre de matchs gagnés par chaque camp, connu seulement si les 7 matchs sont joués. `SetLineup` (remplace la composition ; seulement des joueurs de l'effectif ; contrôle structurel, pas de genre car il n'est pas connu), `SetMatchResult` (**un seul match**, pour saisir au fur et à mesure : `PUT /interclubs/fixtures/{id}/matches/{slot}/result`, les autres matchs ne sont pas touchés) et `SetFixtureResult` (les 7 matchs d'un coup, 409 avant le jour de la rencontre) sont réservés au capitaine et au bureau. `InterclubsEraser` retire une personne supprimée des compositions. **Rencontre en cours (« en direct »)** : `ListFixtures` accepte `when=live` (`FixturePeriods.Live`) et la règle est dans `LiveFixtures.IsLive` (dossier de la feature) : rencontre du jour (Paris), les 7 matchs pas tous décidés, et l'heure de Paris dans une fenêtre qui ouvre 15 min avant le début et dure 5 h (toute la journée si l'heure n'est pas connue) ; chaque `ListFixturesItem` porte `DecidedMatches`, `ClubMatches`, `OpponentMatches` et `IsLive` (le score partiel) pendant que `ClubScore`/`OpponentScore` restent le score final. Côté site, le bandeau `LiveFixturesBanner` (exporté par l'`index.ts` du module, posé par `app.ts`) l'affiche aux adhérents à jour. Pas encore de journal d'audit propre ni de classement de poule.
- **Qui peut jouer en interclubs** : seuls les adhérents **licenciés au club** (adhésion `internal`). Un licencié dans un autre club (`external`) joue les interclubs pour celui-ci : `TeamRules.CanPlayInterclubs(membership)` (règle pure du `Core`, qui lit `MembershipStatus.Kind`) le refuse à l'ajout (400) et l'écarte de la liste des candidats. Le module lit les adhésions par `IMembershipReader` (`GetAsync` pour une personne, `GetAllAsync` pour trier une liste entière sans interroger saison par saison). Une personne sans adhésion validée n'est pas refusée par cette règle.
- **Un joueur, une équipe par saison** : une personne ne peut appartenir qu'à **une seule équipe pour une saison donnée**. `ListTeamCandidates` ne propose donc que les adhérents actifs qui ne jouent dans aucune équipe de la saison, et `AddTeamMember` répond 409 si la personne joue déjà ailleurs cette saison (la règle interroge la base : elle reste dans chaque handler, méthode `PlaysInAnotherTeamThisSeasonAsync`). Retirer la personne de son équipe la rend de nouveau disponible ; les saisons précédentes ne comptent pas.
- **Équipes d'interclubs** : une équipe appartient à une **saison** du club (`Team.SeasonId` → table `seasons`), jamais à un libellé saisi à la main : le nom d'une équipe est unique dans sa saison, et le site n'affiche plus la saison à côté du nom (un filtre de saison, positionné sur la saison en cours, est commun au calendrier et aux équipes — `SeasonFilter` côté site). Le module `Interclubs` lit les saisons par `ISeasonReader` (`Administration/Core`) et expose `ISeasonTeams` pour que la suppression d'une saison soit refusée (409) tant qu'elle porte des équipes.
- **Titres du bureau** : liste libre gérée par le bureau ; un titre = un titulaire ; une personne = un titre ; perdu en quittant le bureau. **Composition du bureau** : `ListBoardMembers` (`GET /club/board`, politique `Member`) donne aux adhérents le nom, l'e-mail et le titre de chaque membre actif du groupe `Bureau` ; c'est la source de la page « Le club » du site (jamais de nom écrit dans le code), et elle reste fermée aux visiteurs.
- **Boîte du club** : le bureau écrit depuis `contact@badpig.fr`, hébergée chez le fournisseur de courrier, et la lit dans un vrai client (webmail, IMAP). L'application ne remplace pas ce client : elle dit seulement sur `/admin` qu'il y a du courrier en attente, à côté des adhésions à valider et des commandes à remettre. Tout ce qui parle au serveur de courrier est dans `Shared/Mailbox/` (`ImapMailboxReader`, `MailboxOptions` : `internal`), comme `Identity/` et `Payments/` ; les modules n'utilisent que `IMailboxReader`. La boîte est ouverte **en lecture seule** et seuls les identifiants des messages non lus sont demandés : aucun message, expéditeur ni objet n'entre dans l'application, rien n'est stocké ni marqué comme lu (RGPD). La réponse est gardée une minute (`ImapMailboxReader` est un singleton) et le serveur a 8 secondes pour répondre. Feature `GetMailboxStatus` (`GET /admin/mailbox`, politique `Board`) ; réglages `Mailbox__Host` (vide = fonctionnalité éteinte), `Port`, `User`, `Password` (secret), `WebmailUrl`. Une boîte injoignable est journalisée en avertissement, jamais une erreur pour le bureau.
- **E-mails au bureau** : `BoardMailer` (`Shared/Core/Mail`) est le seul chemin des e-mails adressés « au bureau » (nouvelle commande, stock bas). Destinataires : l'adresse du club si elle est configurée, sinon chaque membre **actif, Bureau/Admin, et qui s'est déjà connecté** (`AccountRules.HasCompletedSignup`, règle partagée). Une personne invitée au bureau qui n'a jamais confirmé son inscription ne reçoit que son invitation : son adresse n'est pas vérifiée, et ces e-mails portent le nom d'un acheteur et le détail de sa commande.
- **Liste des adhérents** : `ListUsers` accepte `group=members|board|admin` (`UserGroupFilters`, dans le dossier de la feature). Tout le monde étant dans `Membres`, `members` désigne les **adhérents simples** (ni Bureau ni Admin). Le nombre de membres du bureau servant à la règle « il reste toujours un membre du bureau » est compté sur **tout le club**, jamais sur la page filtrée. Côté site, des pastilles `.chip` et le total affiché au-dessus de la liste.
- **Comptes désactivés** : supprimés automatiquement après un mois (sauf Bureau/Admin).
- Abandonné volontairement : e-mail de notification à la personne qui invite ; numéros de référence dans le journal.

## Commandes utiles

- API (compilation) : `cd api && dotnet build BadPig.sln` ; BFF : `cd bff/src/BadPig.Bff && dotnet build`
- Tests de l'API (Docker doit tourner) : `cd api && dotnet test BadPig.sln` ; `BADPIG_TEST_DB_REUSE=true` garde le conteneur PostgreSQL entre deux exécutions (plus rapide en local). `BADPIG_TEST_DB_PORT` et `BADPIG_TEST_DB_PASSWORD` fixent le port et le mot de passe de la base de test pour s'y connecter (utilisateur et base `postgres`) ; le mot de passe reste dans l'environnement de l'utilisateur, jamais dans le dépôt.
- Site : `cd web && npm ci && node scripts/check-module-boundaries.mjs && npx ng build` (puis ne pas committer `dist/` ni `.angular/`)
- Le déploiement du test se fait par GitHub Actions à chaque push sur `develop` ; la production (branche `main`) viendra plus tard.
